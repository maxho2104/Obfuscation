# План реализации: Система автоматизации учёта и отправки/приёма внутренней корреспонденции

## Цель

Создать десктопное приложение для автоматизации деятельности делопроизводства территориально-распределённой сети научных организаций: учёт, отправка/приём внутренней корреспонденции, планирование научных задач, статистика и отчётность.

## Архитектура и стек

- **Язык**: Python 3.10+.
- **GUI-фреймворк**: PyQt5 (Qt for Python).
- **ORM**: SQLAlchemy 2.x.
- **Миграции БД**: Alembic.
- **Базы данных**:
  - Филиал: SQLite, локальный файл на изолированной ПЭВМ.
  - Головной офис: PostgreSQL, локальный или центральный сервер; поддержка одновременной работы нескольких операторов.
- **Сборка и распространение**: pyproject.toml + PyInstaller (Windows `.exe` и Linux-исполняемый файл).
- **Операционные системы**: Windows 7+, AstraLinux 1.6+.
- **Логирование**: стандартный модуль `logging` с ротацией `logging.handlers.TimedRotatingFileHandler`.

## Решённые архитектурные вопросы

### Разделение ролей

- **Филиал**:
  - Редактирует собственную организационно-штатную структуру (отделы, рабочие группы, сотрудники).
  - Создаёт и изменяет научные материалы и телеграммы, заполняет исходящие номера.
  - Создаёт научные задачи, с которыми работает филиал; они синхронизируются с головным офисом.
  - Экспортирует изменения в головной офис.
  - Импортирует оценки и обновления справочников из головного офиса.
  - Видит справочники только для чтения.

- **Головной офис**:
  - Управляет справочниками (территории, филиалы, страны, научные звания, задачи, потребители, руководители).
  - Видит ОШС всех филиалов только для чтения.
  - Присваивает входящие номера материалам/телеграммам.
  - Выставляет оценки.
  - Импортирует данные из филиалов.
  - Экспортирует оценки и обновления справочников в филиалы.
  - Формирует статистику и отчёты по всей сети.

### Синхронизация через экспортные файлы

- Механизм «Изменение» (delta-tracking):
  - Каждая редактируемая сущность имеет nullable `change_id`.
  - Таблица `changes` содержит: `id`, `entity_name`, `entity_pk`, `changed_at`, `changed_fields` (JSON-массив имён полей или спецсимвол для удаления).
  - При повторном изменении до экспорта: `changed_at` обновляется, множество полей объединяется.
  - Экспорт формирует JSON только с изменёнными полями и прикреплёнными файлами, упакованными в ZIP.
  - После успешного экспорта соответствующие записи `changes` удаляются, `change_id` сбрасывается в `NULL`.
  - Удалённые записи помечаются спецсимволом/словом в `changed_fields`.

- Разрешение конфликтов:
  - **Научные задачи**: данные головного офиса побеждают данные филиала.
  - **Материалы / телеграммы**: филиал не редактирует входящие номера и оценки; остальные изменения филиала принимаются головным офисом с оповещением оператора о конфликте.
  - **Справочники**: головной офис абсолютно авторитетен.
  - **ОШС**: филиал авторитетен для своей структуры.
  - UUID формируются с привязкой к филиалу для исключения коллизий.

### Безопасность экспортных файлов

- ZIP-архив не шифруется.
- Безопасность передачи обеспечивается организационно-техническими мерами организации.

### Настройки

- Хранятся в `.ini`-файле в каталоге приложения (`configparser`).
- При отсутствии INI-файла показывается мастер первого запуска.
- Параметры: подключение к БД (URL SQLAlchemy), расположение файлового хранилища, роль, идентификатор филиала.

### Логирование и резервное копирование

- Логи: `<app>/Logs/<YYYY-MM-DD>.log`, ежедневная ротация, хранение 30 дней (`TimedRotatingFileHandler`).
- Уровни: DEBUG, INFO, WARNING, ERROR.
- Автоматический бэкап SQLite перед структурными изменениями и импортом: `<app>/Backups/<YYYY-MM-DD_HH-MM-SS>/`.
- Оператору показывается краткое сообщение; технические детали — в лог.

### Многопользовательский доступ

- Оптимистичный контроль версий (`row_version`) для редактируемых сущностей.
- Транзакционная обработка групповых операций (удаление, импорт, экспорт) через SQLAlchemy сессии.

## Структура файлового хранилища

- Корень задаётся в настройках.
- Прикреплённые файлы:
  - `<storage>/Файлы/Научные материалы/<YYYY-MM-DD>/<исходящий_номер>/`
  - `<storage>/Файлы/Телеграммы/<YYYY-MM-DD>/<исходящий_номер>/`
- Шаблоны отчётов: `<storage>/Шаблоны/`.
- Логи: `<app>/Logs/`.
- Бэкапы: `<app>/Backups/`.
- Экспортные копии: `<storage>/Экспорт/`.

Хранилище проектируется с учётом возможного будущего использования в RAG (например, индексация файлов, поиск по содержимому).

## Риски

- **SQLAlchemy + PyQt5**: требуется проверить стабильность работы с SQLite и PostgreSQL на целевых платформах.
- **Производительность на слабом железе**: большие таблицы и N-N связи могут замедлять UI; требуется пагинация, lazy-loading и кэширование запросов.
- **Синхронизация**: одновременное редактирование задач в филиале и головном офисе требует чётких правил и информирования оператора.
- **Сборка под AstraLinux**: возможны сложности со старыми версиями Qt/PyQt5 и зависимостями.
- **RAG/LLM в будущем**: текущая структура файлового хранилища должна оставаться расширяемой без рефакторинга.
