# Модуль «Задачи» — согласованная спецификация (v3)

Документ фиксирует решения, принятые по итогам обсуждения. Реализация ведётся
по этому файлу; при расхождениях с README приоритет у этого документа.

## 1. Назначение

Отдельная вкладка «Задачи» для распределения научных задач по иерархии:

```
Организация          ← виртуальный корень, только головной офис
└── Регион
    └── Филиал
        └── Отдел
            ├── Сотрудник
            └── Рабочая группа   ← терминальный уровень
                └── Сотрудник    ← справочно
```

Задача назначается сверху вниз: организация → регион → филиал → отдел →
сотрудник или группа. Назначить задачу узлу можно только если она уже есть у его
родителя. Розовым подсвечиваются задачи, которые есть у узла, но не распределены
ни одному его потомку.

## 2. Данные

### 2.1. Таблица `added_tasks`

Одна таблица на все уровни:

```
added_tasks
  id           UUID PK
  task_id      String(50)  NOT NULL  FK scientific_tasks.id ON DELETE CASCADE
  node_type    String(20)  NOT NULL  -- region|branch|department|workgroup|employee
  node_id      String(50)  NOT NULL
  change_id    UUID NULL FK changes.id ON DELETE SET NULL
  row_version  Integer NOT NULL DEFAULT 1
  created_at   DateTime
  UNIQUE (task_id, node_type, node_id)
  INDEX (node_type, node_id)
  INDEX (task_id)
```

`node_id` — строка: коды региона/филиала и UUID отделов/групп/сотрудников в
строковом виде. Полиморфный узел не даёт FK, поэтому целостность узла
проверяется сервисом и валидатором импорта.

`AddedTask` — полноценная tracked-сущность: `ChangeTrackedMixin` +
`VersionedMixin`, класс в `orm/models.py`, запись в `_TRACKED_TABLES`. Экспорт
находит класс через `resolve_entity_class`, импорт применяет назначения
существующим `_upsert`. Метка сущности — «Назначение задачи», поля — через
`orm/labels.py` и секцию `entities` пакета.

### 2.2. Что удаляется

- `ScientificTask.employees` и `task_employee_association`;
- `Employee.tasks` (обратная связь);
- таблица `task_employees`.

### 2.3. Период в назначении не хранится

Назначение — свойство задачи. Задача, попадающая в два финансовых года, показывает
одно и то же распределение в обоих; снятие в одном периоде снимает везде.

### 2.4. Миграция

Новая ревизия после `c4a8f1b2d3e4`:

- `create_table("added_tasks")` с `sa.UUID()`, уникальным и обычными индексами;
- `drop_table("task_employees")`;
- downgrade: пересоздать `task_employees` (`task_id String(50)`,
  `employee_id UUID`, PK, оба FK CASCADE), затем удалить `added_tasks`;
- данных не переносим — стартуем с пустых назначений.

Проверка на SQLite (batch-режим) и PostgreSQL; отдельный скрипт
`scripts_dev/test_migration_task_distribution.py`.

## 3. Иерархия, родители, права

### 3.1. Родитель узла

| Узел | Родитель | Назначение |
|---|---|---|
| Организация | — | нет, это пул задач |
| Регион | Организация (ГО) / — (филиал) | да, из пула |
| Филиал | Регион | да, из задач региона |
| Отдел | Филиал | да, из задач филиала |
| Сотрудник (под отделом) | Отдел | да, из задач отдела |
| Рабочая группа | Отдел | да, из задач отдела |
| Сотрудник (под группой) | Группа | нет, справочный узел |

Рабочая группа — лист распределения: задача назначается группе целиком и
сотрудникам группы автоматически не размножается. Сотрудники под группой
показываются, потому что человек в ней состоит; выбрать такого сотрудника можно,
чтобы посмотреть его задачи, но кнопки назначения/снятия для него недоступны с
подсказкой «назначение сотруднику — в отделе».

Сотрудник, состоящий в группе, отображается дважды — в отделе и в группе. Это два
представления одного узла `employee`, а не две записи. Принадлежность к группе для
отображения определяется по `working_group_id` и датам
`workgroup_start_date`/`workgroup_end_date` на текущую дату.

### 3.2. Права

| Операция | Головной офис | Филиал |
|---|---|---|
| Видит регионы | все | только свой |
| Видит чужие филиалы | да | нет |
| Назначает на регион | да | нет |
| Назначает на филиал | да | да, свой |
| Снимает с филиала | да, если ниже пусто | **нет** |
| Назначает отдел/группу/сотрудника | да | да, в своём филиале |
| Создаёт задачи | да | да |
| Импортирует задачи | да | да |
| Редактирует задачи | все | только назначенные внутри своего филиала |
| Удаляет задачи | да | нет, отмена — через срок |
| Выгружает задачи региону | да | нет |

Головной офис может назначать и ниже региона — это административное исправление
ошибок.

### 3.3. Операции

- **`>>>`** — назначить все выделенные задачи среднего списка выбранному узлу.
  Повторное назначение игнорируется уникальным индексом.
- **`<<<`** — снять все выделенные задачи правого списка. Если у узла есть хотя бы
  один потомок с этой задачей — операция запрещена целиком, сообщение перечисляет
  мешающие узлы.
- **Филиал не снимает задачу с самого филиала.** Убрать ошибочно взятую задачу
  можно только изменением её срока.
- **Автоназначение региону.** Когда филиал назначает задачу себе, строка
  `(task, region)` создаётся автоматически, если её нет. Филиал её не снимает.
- **Создание.** Задача назначается выбранному узлу и всем предкам
  (регион → филиал → отдел → группа). Если у головного офиса узел не выбран —
  задача остаётся в пуле организации.
- **Импорт.** Головной офис: пул, либо выбранный узел и предки. Филиал: задача
  попадает **только в пул региона**, чтобы филиал затем забрал её себе кнопкой
  `>>>`.
- **Неактивные узлы** — серые; `>>>` запрещён, `<<<` разрешён для очистки.
- **Удаление задачи** — назначения каскадом. Если задача связана с материалами или
  телеграммами, удаление блокируется: «Задача используется в документах». В экспорт
  уходит только маркер удаления задачи, назначения на стороне головного офиса
  снимаются каскадом.
- **Удаление узла ОШС** пока не обрабатываем: `node_id` без FK может стать
  висячим. На чтении такие строки пропускаются с предупреждением в лог; позже —
  отдельный сервис очистки.

### 3.4. Розовая подсветка

| Владелец списка | Потомки | Розовый |
|---|---|---|
| Организация | регионы | да, если ни одному региону |
| Регион | филиалы | да |
| Филиал | отделы | да |
| Отдел | сотрудники + группы | да |
| Группа | — | нет |
| Сотрудник | — | нет |

Задача, назначенная группе, считается распределённой для отдела, даже если
сотрудникам группы не назначена. Розовый приоритетнее жёлтой подсветки
«не экспортировано».

## 4. Периоды

Финансовый год: **1 октября — 30 сентября**. Для 12.11.2026 текущий —
`2026–2027`, следующий — `2027–2028`.

Задача попадает в период `[01.10.Y, 30.09.Y+1]`, если:

```
start_date <= 30.09.Y+1  AND  (end_date IS NULL OR end_date >= 01.10.Y)
```

- задача с открытым концом попадает во все годы, начиная с года старта, если
  начало не позже конца периода;
- задача, выходящая за границы года, попадает в каждый год пересечения;
- изменение срока может убрать задачу из периода, но назначения остаются в БД.

Список периодов: все годы, в которые попадает хотя бы одна задача, плюс текущий и
следующий. Сортировка по убыванию, по умолчанию текущий. Подпись `2026–2027`, в
тултипе `01.10.2026–30.09.2027`. Одна задача может отображаться в нескольких
периодах — это нормально.

## 5. Интерфейс

Новая вкладка **«Задачи»** между «Телеграммами» и «Статистикой».

```
[Период: 2026–2027 v]                                  [Обновить]
+------------------+  +----------------------+  +----------------------+
| Дерево           |  | Задачи родителя      |  | Задачи узла          |
| Организация      |  | [поиск............]  |  | [поиск............]  |
|  Регион          |  | Код | Наименование   |  | Код | Наименование   |
|   Филиал         |  | ...                 |>>| ...                  |
|    Отдел         |  | ...                 |<<| ...                  |
|     Сотрудник    |  +----------------------+  +----------------------+
|     Группа       |                          [Создать] [Загрузить] [Выгрузить]
|      Сотрудник   |
+------------------+
```

- `QSplitter` на три области; ширины регулируются.
- Над деревом — комбобокс периода. Над каждой таблицей — строка поиска.
- Между таблицами — вертикально `>>>` и `<<<`.
- Под правой таблицей — «Создать задачу», «Загрузить задачи», «Выгрузить задачи»
  (последняя только ГО).
- Колонки: Код, Наименование, Тип (метка), Начало, Окончание, Частичное решение,
  Полное решение, Комментарий. Даты `dd.mm.yyyy`, пустой конец — пусто, пороги с
  двумя знаками.
- Сортировка по клику, по умолчанию код; по сырым значениям, а не по
  форматированному тексту.
- Выделение `ExtendedSelection`, построчное; кнопки работают со всем выделением.
- Двойной клик и контекстное меню — «Изменить задачу…», «Удалить задачу» (если
  разрешено).
- Drag&drop: средняя → правая — назначить, правая → средняя — снять.
  Перетаскивание на узел дерева — вторая итерация.
- Нет родителя (Организация; Регион в режиме филиала): правая таблица и кнопки
  скрыты, средняя показывает задачи узла.
- Пустые узлы показываются, таблицы пустые, без падений.
- Неактивные — серый текст, назначение запрещено.
- Подтверждение — только при снятии 5 и более строк. Назначение без подтверждения.
- Сотрудник под группой: выбор показывает его задачи, кнопки недоступны.

## 6. Жизненный цикл задачи

### 6.1. Создание и редактирование

Диалог на базе `ScientificTaskDialog`:

- код — только при создании, при редактировании read-only (PK);
- наименование — обязательно;
- тип — комбобокс `enum_labels("scientific_task_type")`, хранится код;
- начало — обязательно, по умолчанию сегодня;
- окончание — необязательно: чекбокс «Бессрочная» или корректная обработка пустого
  `QDateEdit`. Сейчас `get_data()` всегда возвращает дату, и пустое окончание
  превращается в `1900-01-01` — это исправляется;
- частичное/полное решение — числа ≥ 0; «частичное ≤ полное» — предупреждение, не
  блок;
- комментарий;
- проверки: `end_date >= start_date`, код уникален.

Удаление: подтверждение; при связях с материалами/телеграммами — блок; иначе
каскад назначений. Удаляет только головной офис.

### 6.2. Импорт XLSX

Лист **«Научные задачи»**, заголовки: `Код`, `Наименование`, `Тип`,
`Начало действия`, `Конец действия`, `Комментарий`, `Частичное решение`,
`Полное решение`.

- чтение через `_read_sheet_rows`/`_date_from_value` из `reference_import.py`;
- тип — код перечисления; при необходимости метка сопоставляется с кодом;
- upsert по коду: головной офис обновляет все поля; филиал обновляет существующие
  задачи значениями из файла (головной офис авторитетен), новые создаёт;
- после импорта: ГО — пул или выбранный узел с предками; филиал — **только
  регион**, чтобы задача появилась в среднем списке региона и филиал забрал её
  через `>>>`;
- результат: «создано / обновлено / пропущено / ошибки» с номерами строк;
- код задачи глобально уникален; два филиала с одинаковым кодом столкнутся при
  обмене. Рекомендуется префикс филиала в коде, но это соглашение, не проверка.

### 6.3. Выгрузка задач для региона

Это не отчёт о распределении, а файл передачи: **один регион — один XLSX**.

- Кнопка «Выгрузить задачи» (только ГО) в панели задач.
- Диалог: регион (комбобокс, включая «Все регионы»), период берётся из вкладки,
  папка/файл.
- Один регион — `getSaveFileName`, имя по умолчанию
  `Задачи_<код региона>_<период>.xlsx`, например `Задачи_77_2026-2027.xlsx`.
- «Все регионы» — `getExistingDirectory`, в папке создаётся по файлу на регион;
  регионы без задач пропускаются с сообщением.
- Содержимое: лист **«Научные задачи»**, строка 1 — те же заголовки, что у импорта.
  Файл сразу пригоден для импорта филиалом.
- Строки: задачи, назначенные этому региону и попадающие в выбранный период;
  сортировка по коду. Задача, назначенная нескольким регионам, попадает в файл
  каждого.
- Тип — код перечисления, даты — даты с форматом `dd.mm.yyyy`, пустой конец —
  пустая ячейка, пороги — числа.
- Оформление: жирная шапка, автофильтр, закрепление, ширины колонок.
- Назначения внутри региона в файл не входят — филиал распределяет их у себя и
  возвращает дельта-обменом.
- Если у региона нет задач — файл не создаётся, выводится предупреждение.
- Чтобы задача попала в файл, её сначала назначают региону в дереве.

## 7. Интеграция

- **Change tracking:** `AddedTask` в `_TRACKED_TABLES`; метки — `labels.py` +
  `entities` пакета, иначе упадёт `test_entity_labels`.
- **Экспорт ZIP:** работает автоматически — `resolve_entity_class("AddedTask")`,
  `to_dict` сериализует `task_id/node_type/node_id`.
- **Импорт ZIP:** `_upsert` разрешает `task_id` как зависимость; для `node_id` —
  валидатор: узел существует, принадлежит допустимому филиалу, роль не чужая.
  Дополнительно проверяется уникальная тройка `(task_id, node_type, node_id)`: если
  назначение уже есть с другим UUID, строка не создаётся повторно. Ошибка —
  `conflicts`, запись пропускается, импорт продолжается.
- **Статистика:** не затрагивается, она считает `document.tasks`, а не
  `ScientificTask.employees`.
- **Строки:** новые ключи в `AppStrings`, затем
  `scripts_dev/update_pack_strings.py`. В новом виджете никаких русских литералов.
- **Тема:** поле `Theme.unassigned_row` (светлая `#F9D6DA`, тёмная `#5C2B30`),
  цвет только из темы.
- **README/WORK_NOTES:** раздел «Задачи», правила, миграция, результаты тестов.

## 8. Производительность

- Дерево ленивое: регионы и филиалы при старте, отделы/группы/сотрудники при
  раскрытии.
- Задачи периода — один запрос при смене периода; назначения — одним `IN`; строим
  `dict[task_id] -> set(node_key)`.
- Для выбранного узла заранее считается множество потомков; розовый — O(1) на
  задачу.
- Поиск и сортировка в памяти, как в `SqlAlchemyTableModel`.
- Индексы `(node_type, node_id)`, `(task_id)`, уникальный
  `(task_id, node_type, node_id)`.
- При десятках тысяч задач — пагинация и серверный поиск, но в v1 это
  преждевременно.

## 9. План

1. **ORM + миграция + tracking** — `AddedTask`, удаление `task_employees`,
   миграция, `_TRACKED_TABLES`, метки, тест миграции.
2. **Сервис распределения** — дерево, периоды, назначение/снятие, проверка
   потомков, авторегион, права, розовый.
3. **CRUD задач** — диалог, создание/редактирование/удаление, импорт XLSX,
   результат импорта.
4. **Виджет** — вкладка, сплиттеры, таблицы, поиск/сортировка/выделение, кнопки,
   контекстное меню, drag&drop, тема.
5. **Выгрузка по регионам** — один файл на регион, совместимый с импортом.
6. **Тесты и документация** — сервис, права, импорт/экспорт, виджет offscreen,
   README/WORK_NOTES.

## 10. Критерии приёмки

- миграция поднимается и откатывается на SQLite, проверена на PostgreSQL;
- головной офис видит «Организация → все регионы», филиал — только свой регион и
  ниже;
- `>>>` работает только от родителя и идемпотентна; `<<<` блокируется при
  назначениях у потомков; филиал не снимает с филиала;
- розовые строки соответствуют правилу, группа и сотрудник не подсвечиваются;
- периоды считаются по пересечению, текущий и следующий всегда в списке, по
  умолчанию текущий;
- создание/редактирование/удаление задач, импорт XLSX с отчётом об ошибках;
- выгрузка создаёт по одному файлу на регион с заголовками импорта и только
  задачами этого региона и периода;
- филиал импортирует файл и видит задачи в пуле региона, затем забирает их через
  `>>>`;
- назначения попадают в ZIP и применяются в головном офисе; чужой/отсутствующий
  узел и дубль тройки дают конфликт, а не висячую строку;
- все строки — через `AppStrings`, цвет — через `Theme`, метки — через
  `labels.py`/пакет;
- `pytest` зелёный, README и WORK_NOTES обновлены.
