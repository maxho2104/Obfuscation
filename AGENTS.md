# AGENTS.md — правила доработки проекта «Внутренняя корреспонденция»

Этот файл — обязательные правила для любого агента (или человека), который меняет код.
README описывает предметную область и ТЗ; здесь — инварианты, нарушение которых ломает
приложение или обмен данными. Перед правками прочитай также README.md и WORK_NOTES.md
(там история решений и backlog).

## Быстрая проверка перед сдачей работы

1. `.venv/Scripts/python.exe -m pytest tests -q` — все тесты зелёные, без исключений.
2. `PYTHONPATH=. .venv/Scripts/python.exe -c "import internal_correspondence.gui.application"` — импорт GUI не сломан.
3. Если менялась схема БД — есть миграция Alembic с переносом данных (см. ниже).
4. Если менялись строки интерфейса — регенерирована секция `strings` пакета
   (скрипт `scripts_dev/update_pack_strings.py`).
5. Если менялась структура данных или поведение — обновлены README.md и WORK_NOTES.md.

## Инвариант 1: пакет предметной области (white-label)

Главная идея проекта — отделение бизнес-логики от значений. Нарушать нельзя.

- **Коды перечислений неизменяемы.** Код хранится в БД и экспортных файлах. Менять можно
  только метки и веса. Выведенные из употребления значения помечаются `deprecated: true`,
  но не удаляются и не переиспользуются.
- **Никаких захардкоженных значений перечислений** в коде. Метки — только через
  `enum_label()/enum_labels()/enum_codes()` из `core/domain_pack.py`.
- **Никаких захардкоженных русских строк в GUI.** Новые пользовательские строки — только
  новые поля в `AppStrings` (`utils/string_resources.py`), дефолт = осмысленный русский текст,
  шаблоны с именованными плейсодерами (`{error}`, `{count}`). После добавления ключей —
  запустить `scripts_dev/update_pack_strings.py` (регенерирует секцию `strings` в
  `core/domain_pack.default.json`).
- **Метки сущностей и полей** — через `orm/labels.py` (`entity_label`, `field_label`,
  `field_form_label`...), не строками в диалогах. Новые поля моделей снабжать
  `info={"label": ...}` и зеркалить в секции `entities` пакета.
- **Имена служебных директорий** — только через `dir_name("ключ")` из пакета.

## Инвариант 2: change tracking и обмен ZIP

Приложение обменивается дельтами между филиалом и головным офисом; механизм обобщённый,
поэтому правила жёсткие:

- Новая редактируемая сущность → добавить её таблицу в `_TRACKED_TABLES`
  (`services/change_tracking.py`) и наследовать `ChangeTrackedMixin`.
- **Связь N-N: владелец — та сторона, чей FK идёт первой колонкой ассоциативной таблицы.**
  От этого зависит, с какой стороны связь трекается и экспортируется. Для документов
  (материал/телеграмма) владелец — документ.
- Экспорт/импорт сериализует только поля из `Change.changed_fields`; новые поля и связи
  должны попадать туда автоматически — проверяй тестом, а не вручную.
- В каждый экспортный ZIP пишется `meta.json` с `pack_id`/`pack_version` — формат не ломать.

## Инвариант 3: схема БД и миграции

- Любое изменение `orm/models.py`, влияющее на схему → миграция в `alembic/versions/`
  с **переносом существующих данных**; потерьный downgrade — только с явным комментарием.
- Миграции обязаны работать и на SQLite (batch-режим `op.batch_alter_table`, именованные
  FK в `downgrade`), и на PostgreSQL. Проверка — как минимум на SQLite
  (пример: `scripts_dev/test_migration_tasks_nn.py`).
- Первичные ключи: справочники — короткие строковые коды; ОШС, документы, файлы,
  адресация, оценки — UUID; `changes.id` — Integer autoincrement (таблица транзитна).

## Инвариант 4: совместимость СУБД и ОС

- Код не зависит от СУБД: никаких SQLite-/PostgreSQL-специфичных конструкций вне миграций.
- Windows 7+ и AstraLinux: пути — только через `pathlib`, без `os.sep` и веток по ОС.

## Стиль

- Докстринги и комментарии — на русском; идентификаторы — на английском.
- Типизация обязательна (аннотации SQLAlchemy 2.0 `Mapped[...]`, подсказки в сигнатурах).
- На каждое изменение поведения — тест в `tests/`; фикстура БД — временная SQLite
  (шаблон `db_manager` в любом существующем тестовом файле), Qt-тесты — с
  `QT_QPA_PLATFORM=offscreen` (см. `tests/test_statistics_service.py`).
- Тестовые данные для ручной проверки — `tests/seed_data.py` (скрипт сидирования).

## Оформление результата работы

- Каждый этап работ завершать записью в `WORK_NOTES.md`: что изменено (по файлам),
  как проверено (результат pytest), что отложено.
- При изменении структуры данных — синхронно править раздел «Предполагаемая структура
  обрабатываемых данных» в README.md.
